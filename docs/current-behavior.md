# Current behavior

> Status snapshot: 2026-10-30. Automated implementation checks are green. Live browser and Relay acceptance still needs to be run by the user.

The server initializes one Owner row and starts without an email, password, TOTP, Passkey, or recovery-code ceremony. When remote Relay access is configured and no device exists, it prints one five-minute, single-use URL and terminal QR on TTY. The public URL is `${CODEX_APP_ORIGIN}/app/first-session?ref=...`; it contains only a short bootstrap reference. The grant and authorization material remain in the Owner process and protected first-session exchange, and the reference is registered with Relay only while the Owner is online.

App origin, WebAuthn RP ID, and Relay URL are controlled by validated profiles. Development defaults are `http://localhost:5173` / `localhost`; production requires a configured HTTPS origin and matching RP ID. The browser reads the Relay endpoint from `VITE_CODEX_REMOTE_RELAY_URL` rather than from QR contents.

Bootstrap admission uses `bootstrap_reference`. Owner registers and unregisters the reference through the Relay protocol, and Relay keeps only an in-memory reference-to-node route. Replacement, cancellation, expiry, restart, trust reset, disconnect, replay, client-key binding, and successful one-time consumption are covered by focused tests. A successful redemption verifies the current Owner/node/trust epoch and client key, creates one remote device and session, returns paired credentials through the protected response, and removes the reference route.

Opening a valid `/app/first-session?ref=...` URL now enters a dedicated connecting state and automatically redeems the one-time reference. On success, the App navigates directly to the workspace. The generic login page remains the fallback for local Passkey login and remote login without a bootstrap reference; it is no longer an intermediate step for a valid first-session link.

Recovery codes are hash-only. Rotation returns ten codes once; recovery consumes one code, requires a new Passkey, rotates the batch, and revokes previous remote sessions. Owner management supports Passkey presence, recovery generation, local enrollment tickets, first-session issuance, device revoke, revoke-all, session revoke-all, trust reset, and ordinary management QR issue/status/cancel/consume. Management QR consumption is an authenticated management operation and does not create a session by itself.

While Owner is running, CLI management commands use versioned NDJSON local IPC with a fixed allowlist. The current deployment boundary is a single local operating-system user; custom Windows named-pipe ACL hardening is out of scope. IPC remains local-only and application-level command validation remains in force. When Owner is stopped, CLI takes the instance lock and runs a short-lived managed runtime. `pnpm db:reset` requires exact `RESET OWNER DATABASE` confirmation and recreates the current schema in one process; it preserves the remote node identity and trusted device records. To obtain another first-session bootstrap after a device has been paired, use the authenticated bootstrap recovery/trust-reset flow rather than database reset alone.

Automated verification currently passes: 115 server tests, protocol and Relay suites, repository typecheck, focused App tests, the full App suite including the previous eight sidebar failures, formatting checks, and `git diff --check`. The remaining step is live acceptance with `pnpm dev`, `pnpm server`, and `pnpm relay`, covering browser bootstrap, QR scan/upload, paired resume, revoke, trust reset, and restart behavior.
